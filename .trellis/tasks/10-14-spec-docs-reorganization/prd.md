# 整理文档职责与测试规范

## 目标与背景
参考相邻 `my-pi-preset` 的 `10-14-spec-docs-reorganization`：README 为概览入口，根目录 docs 承载功能使用/设计说明和测试教程，spec 承载可复用开发规范与必须保持的工程契约，任务材料承载计划与执行证据。本仓库已有此原则，但维护规则分散、docs 中英文混用，worktree spec 混有操作说明。
用户已同意建立整理任务，并要求复用邻仓 tmux 测试文档；随后批准本 PRD 的最终实施范围。

## 范围
1. 保留现有 extension/scripts/guides 层级；新增统一英文文档维护规范并接入索引：内容归属、语言、行为变更同步、引用检查和历史证据边界。
2. spec 文档英文；根 docs Markdown 中文（命令、标识符、代码和上游原文不翻译）；保留 JSON 校验清单原样。README 维持当前概览职责，不堆入详情。
3. 逐段审查 worktree-lifecycle 等现有 spec：保留权限、路径安全、锁/占用、恢复、材料谱系、TS/Python 所有权、错误/副作用等开发契约；具体操作教程和设计解释与现有 docs 对齐，去重但不机械迁移。
4. 复用邻仓 docs/testing/tmux.md 到本仓库同路径，中文操作指南保留隔离、独立 tmux 服务、已有 CLI、最小矩阵、条件等待、新帧判定、错误报告、实际进程退出与清理要求；去除邻仓专属历史链接，按本仓库入口和审批边界适配。quality-guidelines 留通用约束与指南入口，不复制邻仓 pnpm/SDK 配置。
5. 把较长 provider 测试操作整理到 docs/testing 下，quality spec 保留证据分层和必需约束。使用真实源/测试确认命令，不改变测试实现。
6. docs/plans 加明确历史标识和当前文档链接，不重写历史方案或执行结果。维护受影响 README、spec/docs 索引、活动任务引用/JSONL；归档任务原文不批量改写。

## 不做
不改产品代码、测试算法、依赖、配置、runtime/模板/skills/角色、生成资源或来源 hash；不真实运行 tmux/provider、安装、个人同步、reload、push 或归档；不碰并行 runtime-tool-names 和 dispatch-shared-source 的无关内容。

主会话直接实施与文档自检；文档整理不改变公开行为或安全算法。单阶段把规范、docs、导航和活动引用作为一致性整体，核 diff 和检查后提交本任务精确文件（不含并行任务），不自动归档或推送。若发现必须改产品/生成资源才能修复引用，先报告，重新确认范围。
