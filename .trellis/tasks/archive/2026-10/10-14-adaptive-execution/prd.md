# 按需选择实施与检查执行者

## 目标
让默认 Pi workflow 保留规划、授权和验证底线，同时避免简单任务被强制拆成 implement/check 两个子代理。

## 已确认事实与授权
用户已认可完整修改方案，并明确要求实施、workflow 使用英文；随后批准创建轻量任务并实施验证。当前模板和多个 skill 重复要求主会话派发两个角色。现有 CLI 提供 `start --allow-empty-context`，可显式允许未派发角色的空清单，不需要改运行时。

## 范围与要求
- 修改英文内置 workflow：分别选择实施和检查执行者，支持主实施→自查、主实施→独立 check、委派实施→独立 check。
- 所有路径读取相关规范并验证；高风险工作要求独立检查，检查结论不能伪称独立审查或真实验证。
- 按派发角色准备 JSONL，说明现有显式空清单选项及使用边界。
- 同步关联 skills 的派发、规划授权、检查和收尾规则，更新模板/skill 输出 hash，不改历史源 hash 或许可。
- 覆盖文案契约、模板阶段提取与 CLI 空清单行为，运行相关和全套可用测试。
- 用户后续明确批准默认本地阶段提交规则：实施批准包含范围内本地 commit，明确 opt-out 时除外；每阶段检查通过后提交，不等最终收尾，push/历史改写仍需明确授权。
- 政策集中在 workflow，skills 删除重复策略；finish-work 聚焦按已有授权验收后归档/journal/清理绑定。用户最终授权覆盖项目 workflow 并一起提交，未授权 push 或归档。

## 验收标准
- [x] 默认 workflow 为英文，保留解析标题和状态标记。
- [x] 不再强制成对派发，明确支持主会话实施后独立 check。
- [x] 授权可连续执行但不得超范围；本地提交默认随实施批准，opt-out 可不提交；push/历史改写/归档授权独立。
- [x] 阶段提交默认规则与 skill 职责收敛有最终验证证据。
- [x] JSONL 仅按派发角色必需；现有 start 门禁的显式用法可验证。
- [x] 关联技能无旧强制派发/无条件双清单规则，资源 hash 与输出一致。
- [x] 相关测试和全套可用检查有真实结果与限制记录。

## 排除
不修改运行时或无关用户定制文件，不安装、reload、push 或归档。用户最新授权用内置模板覆盖本项目 `.trellis/workflow.md`，并将本任务改动一起本地提交；替代此前不覆盖/不提交边界。模型遵循效果不以静态测试冒充。
